# Zibblu Design System · 跨平台 UI / UX 视觉准则

> **批准来源**：Owner 2026-11-14 对 30 项视觉与交互问题的答复。  
> **状态**：目标设计规范（Accepted direction）；当前 Windows v0.1.1 并非已全部实现。  
> **适用范围**：桌面（Windows/macOS）、手机（Android/iOS）、平板（iPad/Android）及后续新增页面。  
> **权威边界**：视觉规则不覆盖 `docs/SECURITY.md` 的安全限制、不改变 M1/M2/M3 协议与授权模型。

## 1. 核心定位与参考范围

**Zibblu = Apple 式克制、薰衣草色品牌识别、iMessage 主导的精致感、少量 Snapchat 式年轻趣味。**

| 产品参考 | 采用什么 | 不采用什么 |
| --- | --- | --- |
| 微信 WeChat | 聊天列表、聊天操作逻辑、普通文件卡片、个人主页和设置结构 | 不复制微信绿色、不擅自改变 Zibblu 现有消息气泡 |
| QQ | 普通文件的操作效率、完整右键菜单/批量管理、图片视频查看器 | 不照搬其复杂工具栏，不让文件页充斥媒体 |
| iMessage | **视觉效果主要参考**：输入区、控件质感、自然流畅动效与细节打磨 | 不改已认可的现有气泡，不复制平台专有元素 |
| Snapchat | **少量点缀**：轻快、亲切、自然有趣的反馈 | 不用大面积亮黄、荧光配色、夸张动画 |

借鉴的是逻辑与体验，不是临摹其他品牌的独有素材或界面。**任何时候，清晰可用优先于好看的装饰。**

## 2. 规范等级、冲突处理与迁移

- **MUST**：Owner 确认的不可随意偏离的目标；新增 UI 和重构要遵守。
- **SHOULD**：强烈建议的默认实现；因平台约定、可访问性、屏幕限制而偏离时要在 PR 写明。
- **MAY**：按产品实际情况适度发挥。
- 优先级：安全和隐私真实性 > 关键操作可达性/无障碍 > 核心信息架构和交互一致性 > 视觉效果。
- **当前代码不一致 ≠ 自动修改权限**。以本规范记录差距，在单独授权的 UI 实施 PR 逐步调整。不得借“统一视觉”大改服务协议、私聊安全或 AI 权限。
- 所有平台共享**设计语言、语义 Token、图标含义和操作心智模型**，但不是逐像素复刻；桌面、手机、平板遵循各自的输入方式与导航惯例。

## 3. 颜色、字体、图标、材质

### 品牌颜色和主题

- **MUST**：主品牌色为**薰衣草色 Lavender**。普通应用与普通聊天采用**带极轻薰衣草倾向的浅色底色**，高可读内容面板保持明净。
- **MUST**：**私密聊天保持独立深色主题**。当前私聊深色主题先保留，不因全局浅色设计把私聊改为浅色。普通界面本期不新增全局暗色切换要求。
- **MUST**：建立统一的颜色语义 Token，例如 `brand.lavender`、`action.primary`、`surface.canvas`、`surface.panel`、`text.primary`、`text.muted`、`border.subtle`、`private.surface`、`status.error`。不要在页面里自行创造互不兼容的紫色。
- **MUST**：文字、图标、焦点、高亮、危险状态需满足实际平台可访问性；至少按 WCAG AA 检查主要文本和交互对比度。**安全/连接状态不能只靠颜色表示。**
- **精确 HEX 尚未由 Owner 确认**。以下为初次原型候选，**不是已冻结品牌色值**：Lavender `#A78BFA`、高对比操作紫 `#6B46B1`、浅画布 `#F8F6FC`、内容面板 `#FFFFFF`、主文字 `#242033`。正式定值前应提供对照截图和对比度检查。现有 CSS 色值不等于 Owner 最终批准。

### 字体、图标、层次

- **MUST**：正文使用各端**原生系统字体**，尊重系统字体缩放及中英文排版；不强迫全端统一下载同一第三方字体。
- **MUST**：图标默认**线性风格**，已选中项可切换为对应的**实心形态**；相同功能不能在不同页面使用含义冲突的图形。激活状态不应只凭颜色表达。
- **MUST**：以**小圆角**和清晰分组为主（接近微信的克制风格）；阴影少、分隔线轻，拒绝默认全站胶囊式大圆角。**已保留的消息气泡不受此一般圆角规则覆盖**。
- **MUST**：以扁平表面为主；玻璃/模糊**只可适度用于弹窗、浮层、菜单**，需要无模糊回退。禁止全局铺满半透明卡片、渐变、发光和多重阴影。
- **MUST**：采用**微信式平衡信息密度**：可快速扫描，不拥挤也不过分留白；大/小屏都要保持内容层级。
- **SHOULD**：动效自然、流畅，有**适量弹性**，但不持续漂浮、反复弹跳、夸张飞入。常规转场可从 140–240ms 原型起步，最终数值由实际视觉验收确定；尊重减少动态效果设置，不以动画延误发送、输入、切换。

## 4. 跨端导航与布局

| 终端 | MUST 目标结构 | 原生适配 |
| --- | --- | --- |
| 桌面 | **三栏**：主导航 / 会话列表 / 当前内容（微信式） | 鼠标、键盘、右键、快捷键；窗口缩小时合理折叠，避免横向滚动 |
| 手机 | **四个底部入口**：聊天 / 联系人 / 文件 / 我的 | 长按消息、单手触控、层级返回、系统安全区域 |
| 平板 | **双栏**：列表 + 内容 | 支持横竖屏、分屏与浮窗宽度；不简单放大手机 UI |

- **MUST**：Token、信息层级、功能名称及能力边界跨端统一。
- **MUST**：各端允许导航形式和手势因平台而异，不能因“风格统一”牺牲原生可用性。
- **MUST**：手机文件入口仍遵守第 6 节“仅不能在聊天内直接预览、需下载的附件”的内容边界。

## 5. 聊天：微信的结构与逻辑，iMessage 的输入质感

- **MUST**：聊天列表采用**微信式头像—名称—最近消息预览—时间—未读标记**的紧凑清晰排布；不要给每条聊天加独立大卡片。
- **MUST（Owner 指定保留）**：**现在的消息气泡设计保持现状**。未经单独批准，不调整气泡形状、弧度、配色、尾巴、归属侧或整体排布。不因为“参考 iMessage”就重做气泡。
- **MUST**：输入区使用**微信式功能逻辑 + iMessage 式精致视觉**，简洁呈现输入、附件、发送；更多功能收在可发现但不拥挤的位置。
- **MUST**：消息操作以**微信式上下文菜单**为主：桌面右键、移动长按；功能仅显示真实支持且有权限的动作。
- **MUST**：消息反馈**极简**，只突出必要的失败、未读、重试、连接等状态；不使用多余动画/标签装饰每条消息。已有的**双方自愿开启的已读回执**可保留，但不要喧宾夺主。
- **MUST**：已实现的消息历史、离线同步、撤回、引用、可见性、访问权限保持原语义；不要通过外观变更声称新增未实现的送达能力。

## 6. 文件与媒体：QQ 的功能，微信的呈现（核心边界）

### 6.1 互斥的内容组织

- **MUST**：主导航的 **Files / 文件页** **只展示无法在聊天中直接预览、需要下载后查看或使用的普通附件**，如不可直接预览的文档、压缩包、安装包和其他格式。
- **MUST**：**图片、视频不混入文件页**；它们应当在各自会话的聊天记录/“查找聊天内容”里检索，聊天消息中在格式允许时直接预览。
- **MUST**：文件页、会话内文件筛选与媒体历史使用一致的分类原则，不能因后端统一返回附件就重新混合。不同平台无法预览某格式时要提供清晰的下载退路。
- **注意**：现有 Windows 文件中心可能仍展示媒体与全局传输数据，这是待迁移的**实现差距**，不代表本决策已经实现。

### 6.2 文件卡片、传输与管理

- **MUST**：聊天里的普通附件采用**微信式文件卡片**，以类型、名称、大小、必要操作状态为中心，视觉简洁。
- **MUST**：**传输进度直接在对应聊天文件卡片里显示**，微信式交互；暂停/继续/失败/重试等按真实能力呈现。不要把独立全局传输中心作为主要操作入口。
- **MUST**：文件**管理能力**参考 QQ：完善的右键操作、必要批量操作、保存、按类型/时间/名称查找等；高级能力可折叠在二级菜单，但不能为了极简抹掉实用功能。
- **MUST**：图片/视频采用**QQ 式内置媒体查看器**，可用时支持放大、缩小、前后切换、保存、分享等；不支持的能力不放无效按钮。
- **MUST**：继续遵循服务器访问授权、分块、断点续传、完整性校验；媒体分类或进度位置的改变**不授权修改文件安全语义**。

## 7. 个人主页、设置、私聊和 AI

- **个人主页 MUST**：微信式简洁主页；首屏仅突出头像、名称与关键资料，扩展封面/介绍等放在二级页面，不把主页做成社交信息流。
- **设置 MUST**：桌面分栏设置，手机微信式逐级列表，平板自适应；同一设置项的名称、作用与危险提示保持一致。
- **私聊 MUST**：**保留独立深色风格**，与普通聊天共享控件设计但明显区分状态。身份、LAN-only、认证和失败等必须有**文字与图标状态**，不能仅以“深色=安全”作隐私承诺。M2 仍需双方同意、认证加密局域网直连、无公网回退、不持久化、无云 AI。
- **AI MUST**：**视觉存在感尽量低**，仅在 `@自定义名称`、本次授权与必要回复标记时出现；不新增独立 AI 常驻面板或主导航。授权时仍必须清楚展示被外发的消息与文件范围、目标服务与确认，不因为极简而隐藏风险。

## 8. 严禁的三大设计反模式（Owner 选择 30D）

1. **过度装饰**：多余玻璃、渐变、阴影、彩色装饰、过度动效或重复视觉强调。
2. **信息拥挤**：冗余入口、工具栏、标签、默认暴露过多高级功能、影响阅读的布局密度。
3. **交互割裂**：同一操作在不同页面语义/图标/反馈不同；跨端为图形一致而破坏各端习惯。

尤其禁止：将微信操作误解成必须使用微信绿；将 Snapchat 参考误解成大面积明黄；因为 iMessage 参考就重做**已确认保留**的 Zibblu 消息气泡；因为 QQ 文件能力就堆满聊天界面的按钮。

## 9. Agent 实现流程与验收清单

Agent 在做 UI 工作前**必须**同时阅读本文件、`AGENTS.md`、`docs/PRODUCT.md`、`docs/SECURITY.md`。在 PR 中指出本次实现符合的条目、已知差距与平台实测情况。

- [ ] 视觉：Lavender 浅色、轻材质、小圆角、线性图标与原生字体；私聊深色不混用。
- [ ] 聊天：微信式列表与菜单；**现有消息气泡不改**；输入区功能清晰、状态简约。
- [ ] 文件：文件页只列不可直接预览且需下载的普通附件；图片视频从聊天记录查找；文件卡片微信式，进度在聊天内，QQ 式管理能力可达。
- [ ] 主页/设置：首屏简洁；桌面分栏，手机逐级导航。
- [ ] 桌面三栏、手机四入口、平板双栏；键鼠/触控/分屏分别正确。
- [ ] 无安全状态伪装：M2 LAN-only、M3 单次可见范围、服务端普通消息传输语义不被视觉模糊。
- [ ] 动效克制且自然，支持减少动态效果；无过度装饰、信息拥挤、交互割裂。
- [ ] UI PR 提供真实截图或实机验证结果；未验证的平台明确写出，**文档提交不能当作 UI 已完成**。
- [ ] 任何气泡重设计、文件媒体范围反转、私聊主题或 AI 授权简化，需单独征求 Owner 同意。
